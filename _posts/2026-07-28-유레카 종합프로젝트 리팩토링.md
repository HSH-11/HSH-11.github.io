### 프로젝트 소개

유레카 종합프로젝트(요플레)를 **최신 기술 스택 기준으로 재설계·이전**하는 리팩토링 프로젝트입니다.  

| 구분 | Before | After |
|------|-----------------|------------------|
| Backend | Spring Boot 3.5 / Java 17 | **Spring Boot 4.1 / Java 21** |
| 인증 | jjwt 커스텀 필터 + `X-AUTH-TOKEN` | **OAuth2 Resource Server(JWT)** + Bearer |
| AI | Gemini + WebClient 직접 호출 | **Spring AI 2.0 + OpenAI** |
| Chat Memory | 직접 구현 / Redis 수동 | **Spring AI Redis ChatMemory** (예정) |
| Vector / RAG | 임베딩 서비스 분리 | **Elasticsearch VectorStore + RAG** (예정) |
| Frontend | 분홍 테마 · 요금제/챗봇 풀기능 | **보라 테마 · 인증 기능부터 단계적 이전** |

**현재 Phase 진행 상황**

1. ✅ **환경 구성** — 인프라·의존성·JWT Resource Server 스캐폴드  
2. ✅ **인증 리팩토링** — 회원가입 / 로그인 / 로그아웃 / Refresh / 내 정보  
3. ✅ **프론트 인증 UI** — Yoplanit 전용 프론트 신규 구성  
4. ⏳ AI 챗 · RAG · 도메인(요금제→여행 플랜) 이전 — 다음 단계

------

### 리팩토링 목표

1. **표준화된 인증**: 커스텀 헤더/필터 대신 Spring Security OAuth2 Resource Server로 업계 표준 Bearer JWT 적용  
2. **보안·응답 모델 정리**: `permitAll` 우회, 예외 기반 API, Refresh Token Rotation(RTR)  
3. **Spring AI 중심 AI 파이프라인**: WebClient 직접 호출 → `ChatClient` / Advisor / VectorStore  
4. **점진적 이전**: 백엔드에 구현된 기능만 프론트에 노출해, 미이전 도메인(요금제 등)과의 불일치 제거

### 로그인 · 회원가입 리팩토링

기존 요플레 인증을 **기능은 유지·개선하고, 구현 방식은 교체**했습니다.

| 항목 | Before | After |
|------|------------------------|-------------------------|
| 토큰 발급 | jjwt `TokenProvider` | Spring Security **`JwtEncoder`** |
| 요청 인증 | 커스텀 `JwtTokenFilter` | **OAuth2 Resource Server** |
| Access 헤더 | `X-AUTH-TOKEN` | **`Authorization: Bearer`** |
| Refresh | JWT를 Redis `@RedisHash` 키로 저장 | **Opaque UUID** + Redis TTL |
| Subject | email (재발급 시 userId와 혼동) | **userId** + claim(`email`, `roles`) |
| 보안 설정 | `permitAll("/**")` (사실상 비활성) | 공개 API만 화이트리스트 |
| 가입 응답 | 성공 메시지만 → 재로그인 필요 | **가입 즉시 Access/Refresh 발급** |
| 실패 처리 | 서비스에서 `ApiResponse(FAIL)` 직접 반환 | **예외 + `GlobalExceptionHandler`** |
| DTO | `UserDto` 입출력 혼용, password 노출 위험 | Request / Response 분리, password 미포함 |

**API 설계**

| Method | Path | 설명 |
|--------|------|------|
| `POST` | `/api/auth/signup` | 회원가입 (201 + 토큰) |
| `POST` | `/api/auth/login` | 로그인 |
| `POST` | `/api/auth/refresh` | Access/Refresh 재발급 (RTR) |
| `POST` | `/api/auth/logout` | Refresh 폐기 |
| `GET` | `/api/auth/me` | 내 정보 (Bearer 필요) |

Refresh / Logout은 커스텀 헤더 대신 body `{ "refreshToken": "..." }`를 사용합니다.

#### 핵심 구현 포인트

**1) Access Token (JWT) + Refresh Token (Opaque)**

- Access: Nimbus JWT (HS256), claim에 `email`, `name`, `roles`  
- Refresh: UUID를 Redis `auth:refresh:{token}`에 저장, TTL은 설정값과 동기화  
- `rotate()`로 구토큰 폐기 후 신토큰 발급 → **Refresh Token Rotation**

```text
Login/Signup
  → Access JWT 발급 (subject = userId)
  → Refresh UUID 발급 → Redis 저장

Refresh
  → Redis에서 userId 조회
  → 구 Refresh 삭제
  → 새 Access + 새 Refresh 발급
```

**2) 예외 기반 API 응답**

- `BusinessException` 계층 (`DuplicateEmail`, `InvalidCredentials`, `InvalidToken` 등)  
- `GlobalExceptionHandler`가 HTTP 상태 + `ApiResponse`로 매핑  
- Bean Validation(`@Valid`) 실패도 일관된 `INVALIDATED` 응답

**3) User 도메인 정리**

- 테이블명 `user`(예약어) → **`users`**  
- 요금제 Membership FK는 Yoplanit 도메인에 아직 없어 **제외** (점진 이전)  
- 응답 DTO는 password를 절대 포함하지 않음

**4) SecurityFilterChain**

- 공개: signup / login / refresh / logout / swagger  
- 그 외: authenticated  
- JWT `roles` claim → `GrantedAuthority` 변환

**5) 검증**

- `AuthService` Mockito 단위 테스트 (signup / login / refresh / logout)  
- Swagger UI + Bearer Authorize로 E2E 확인  

#### 포트폴리오 관점에서의 의미

- “JWT를 썼다”가 아니라 **왜 커스텀 필터를 버리고 Resource Server로 갔는지**를 설명할 수 있음  
- **표준 헤더 · RTR · opaque refresh · 예외 기반 API**까지 보안/운영 관점을 함께 개선

1. **회원가입 / 로그인**  
   JWT Access + Redis Opaque Refresh, 가입 즉시 토큰 발급

2. 검색·비교 / 추천  
3. AI 챗봇 (Spring AI `ChatClient` + Redis ChatMemory)  
4. RAG · 추천 질문 (Elasticsearch VectorStore)  
5. 금칙어 · 대시보드 · STT

### 트러블슈팅 기록

**JWT 발급 실패: `secret length must be at least 256 bits`**

- 원인: HS256은 시크릿 **최소 32바이트** 필요. `.env`가 `application.yaml`보다 늦게/누락 로드되면 짧은 값으로 서명 시도  
- 해결:  
  - `spring.config.import: optional:file:.env[.properties]`  
  - 시크릿 길이 검증으로 조기 실패
